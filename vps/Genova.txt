# ============================================================
# 5. AUTHENTICATION SYSTEM
# ============================================================

## Auth Providers (src/convex/auth.ts):
1. EmailOTP (custom provider - emailOtp.ts)
2. Password (built-in)
3. Anonymous (guest access)
4. GoogleProvider (ConvexCredentials - pre-verified via googleAuth:verifyGoogleToken)

## Auth Config (src/convex/auth.config.ts):
- Provider 1: Convex self-issued JWTs (iss = CONVEX_SITE_URL)
- Provider 2: Freebuff federated tokens (type: "customJwt", issuer: VLY_CONVEX_AUTH_ISSUER)

## Auth Flow:
1. User → /auth → selects login method
2. signIn() from useAuthActions() → Convex Auth
3. On success → ConvexAuthProvider sets identity
4. useAuth() hook reads: isLoading, isAuthenticated, user (via api.users.currentUser)
5. getCurrentUser(ctx) in backend → getAuthUserId(ctx) → ctx.db.get(userId)

## Key Auth Files:
- src/convex/auth.ts: Auth provider setup
- src/convex/auth.config.ts: JWT config for federated auth
- src/convex/users.ts: getCurrentUser(), currentUser query
- src/hooks/use-auth.ts: useAuth() hook
- src/components/RequireAuth.tsx: Route guard
- src/components/RoleGate.tsx: Role-based route guard

# 6. ROLE & PERMISSION SYSTEM
# ============================================================

## Roles (from schema.ts):
ADMIN = "admin"           # Full system admin
SITE_ADMIN = "site_admin" # Site management admin
USER = "user"             # Regular student
MEMBER = "member"         # Profile-completed member
INSTRUCTOR = "instructor" # Course instructor
MENTOR = "mentor"         # Mentor/tutor
CONTENT_MANAGER = "content_manager" # Content creation manager
SUPPORT = "support"       # Support staff

## Role Assignments:
- Stored in users.role (primary) and users.secondaryRole (secondary)
- Admin assigns roles via adminSetRole mutation (admin-only)
- Users detected as admin via admins table email match

## Access Control Matrix:

### admin (System Admin):
- Full admin panel access
- All CRUD operations on all entities
- User management (create/edit/delete users, set roles)
- Payment management (online + offline)
- Certificate management
- Super admin panel access
- Site Studio full access
- AI Management full access
- Telegram Bot full access
- Academy Path management

### site_admin (Site Admin):
- Same as admin for most operations
- Cannot create/delete system admins
- Site Studio full access
- AI Management full access
- Telegram Bot full access

### instructor:
- Instructor Panel (create rooms, manage classes, whiteboard, broadcasts)

# 10. KEY FEATURE FLOWS
# ============================================================

## Authentication Flow:
1. User visits /auth → selects Google, Email OTP, or Password
2. Frontend calls signIn("google"|"password"|"emailOtp"|"anonymous", credentials)
3. Convex Auth processes → creates/updates user in users table
4. currentUser query returns user data including role
5. RequireAuth checks isAuthenticated → redirects to /auth?returnTo=... if not
6. RoleGate checks user.role against allowed roles → redirects to panelForRole()

## Purchase Flow (Course):
1. User clicks "خرید" on CourseDetail page
2. CheckoutDialog opens with package selection (economy/basic/plus/premium)
3. User selects package → can enter coupon code
4. Frontend calls enroll.purchase({items, bundleTier, couponCode})
5. Backend: validates course exists/published, calculates price from DB (not frontend)
6. Backend: checks payment.enabled in siteSettings
7. Backend: validates coupon (code, active, maxUses, expiresAt)
8. Backend: creates order with status "paid"
9. Backend: creates enrollment record
10. Backend: if AI subscription → creates aiSubscriptions record

## Offline Payment Flow:
1. Student fills form: courseId, tier, amount, trackingNumber, receiptImage
2. Frontend uploads receipt via collab.getUploadUrl() → gets storageId
3. Frontend calls offlinePayments.submitOfflinePayment()
4. Backend: creates offlinePayments record with status "pending"
5. Admin sees in Admin panel → reviews receipt image
6. Admin approves → backend: creates enrollment + order, updates course studentCount

## AI Chat Flow:
1. User opens /ai-chat → sees conversation list + chat interface
2. User creates new conversation → aiChat.createConversation()
3. User types message → aiChat.sendMessage()
4. Backend: checks daily limit (role-based + subscription + quota override)
5. Backend: saves user message to aiMessages
6. Backend: increments aiUsage for today
7. Backend: schedules aiActions.callAI action via scheduler.runAfter(0, ...)
8. Action: reads AI config from aiConfig/aiModels (server-side, key never reaches browser)
9. Action: reads conversation history from aiMessages
10. Action: calls AI provider (OpenAI/Anthropic/Google)
11. Action: saves AI response via internal mutation aiChat.saveAIMessage
12. Frontend: sees response via reactive query subscription

## Telegram Bot Flow:
1. User sends /start [CODE] to Telegram bot
2. Webhook handler: telegramWebhook.handleTelegramWebhook
3. If CODE present → account linking flow (validates code, links telegramId to user)
4. If no code → sends welcome message with inline keyboard
5. Bot commands: /profile, /questions, /sessions, /tasks, /notifications, /groups, /settings
6. Each command: looks up user by telegramId → queries relevant data → sends formatted message
7. Callback queries route to same handlers via callback_data

## Daily Quiz Flow:
1. Admin creates quiz entries for dates via dailyQuizAdmin.createEntry or autoFill
2. Or AI generates questions via dailyQuizAdmin.aiGenerateQuestions
3. Student opens /daily-quiz → tests.getDailyQuiz()
4. Backend: gets today's entries, picks random one, checks if user already answered
5. Student answers → tests.answerDailyQuiz()
6. Scoring: correct = +3, wrong = -1, skip (not answered) = 0
7. Admin views leaderboard via dailyQuizAdmin.getLeaderboard()

## Site Studio Flow:
1. Admin opens /panel/site-studio → SiteStudio component
2. Loads pages from studioPages table
3. Each page has studioElements (blocks) and studioThemes
4. Editor shows draft + published states separately
5. Staff edits elements → changes saved to draft fields
6. On publish: draft fields copied to published fields
7. Public site reads only published fields via listPublishedPages query
8. Version history: each publish creates studioVersions entry
9. Can restore previous versions

- Sellers receive payment from buyers (minus platform commission)
